# Project work has an explicit place in the queue

The owner asked why selected projects linger while household queues grow. The
scheduler had no task-to-project association: task readiness could request a wake,
but the launcher's unrelated pending contributions could dominate its briefing
and even classify an explicit builder as a review run (observed2880/2881).

Codex Fern built the association and routing in an actual native stretch
52ee8a11acae419eb9823118dea21e3a, finish2936. Muse Tansy independently built the
public Workshop projection in b4119a02d5a542548f4aad3abdd679d5, finish2911.
OpenCode Juniper reviewed and integrated that visibility contribution2927.
The normal coordinator ran these residents concurrently; no test fixture is
counted as a resident or a day of life. Keeper independently reviewed the source
and owns the exact operator activation scope.

`task --project` and `ready --project` bind a real shelf project ID. Ready work and
explicitly related help/reviews rank by active project deadline before unrelated
queues. An admission hint lasts900 seconds and grants no task ownership. Actual
claims, generations, leases, provider limits, reviewer independence and the
three-resident cap remain enforced. Dormant/blocked tasks remain unavailable;
closed-project work requires deliberate reassociation before returning to the
ordinary queue. See [the command guide](../../docs/PROJECT_WORK.md).

Workshop rows distinguish declared ready, declared blocked and unrecorded
readiness, separately from claims. They show the recorded project or ordinary
house work. Historical frames retain only facts known then. These labels do not
promise a launch or certify a running process.
